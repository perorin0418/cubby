接続名ごとに別のコンテナで Claude Code を動かす構成

結論：Desktop に登録する SSH 接続の名前を、そのままコンテナ名として使います。名前が同じなら何度つないでも同じコンテナに戻り、名前が違えば別のコンテナになります。新しいコンテナがほしいときは、Desktop に新しい名前の接続を追加するだけです。

この対応づけは、手元の ~/.ssh/config に書く ProxyCommand で実現します。ProxyCommand は「SSH の通信路として、指定したコマンドの標準入出力を使う」という OpenSSH の設定です。ここではリモートホスト上のスクリプト ctr-connect を呼び、接続名のコンテナを用意したうえで、そのコンテナ内の sshd（SSH の接続を受け付けるサーバープログラム）につなぎます。

青い実線が SSH の経路、茶色の破線がマウント、紫の点線が推論の通信です。灰色の細線は「この worktree はこのリポジトリから作った」という関係を表します。色はコンテナごとに分けています。丸数字は次の節の手順番号に対応します。

接続の流れ

  1. Desktop で接続（例 ctr-feature1）を選ぶと、手元の OpenSSH が ~/.ssh/config の Host ctr-* の設定を当てはめます。ProxyCommand に従い、まず remote-host に SSH でログインします。
  2. remote-host 上で ctr-connect ctr-feature1 が実行されます。%n は接続時に指定した名前に置き換わる記号です。スクリプトは ctr-feature1 という名前のコンテナがなければ作り、止まっていれば起動します。
  3. スクリプトは docker exec -i ctr-feature1 nc localhost 22 で、コンテナ内の sshd と標準入出力をつなぎます。nc（netcat）は、標準入出力とネットワーク接続を中継するコマンドです。ポートを外部に公開しないので、コンテナを何個作ってもポートの割り当ては要りません。
  4. コンテナに dev ユーザーでログインできたら、Desktop がそのコンテナの ~/.claude/remote/ に Claude Code 本体を置いて起動します。別の名前（例 ctr-bugfix）で接続すれば、同じ流れで別のコンテナが使われます。

ホスト上のデータの分け方

/home/dev はコンテナごとのボリューム（例 ctr-feature1-home）に保存します。コンテナを作り直しても、Claude Code 本体やセッションの記録が残ります。

作業ディレクトリは git worktree（1つのリポジトリから作業ディレクトリを複数作る機能）で、コンテナごとに /srv/worktrees/<名前> を作ります。worktree の中の .git ファイルは元リポジトリの絶対パスを指しています。そのため、元リポジトリ /srv/project と各 worktree を、ホストと同じパスでコンテナにマウントします。

押さえておく点

  • 全コンテナに同じホスト鍵をイメージで焼き込みます。ホスト鍵は、接続先が前回と同じ相手かを確かめるための鍵です。手元では HostKeyAlias（照合に使う名前を固定する設定）で dev-containers にまとめるので、known_hosts の記録は1つで済みます。
  • イメージには sshd、nc、dev ユーザーの公開鍵を入れておきます。
  • remote-host のログインユーザーは docker を実行できる必要があります。docker グループは実質 root と同じ権限なので、共用ホストでは扱いに注意します。
  • Desktop がパターン指定（Host ctr-*）と ProxyCommand を想定どおり適用するかは未検証です。先にターミナルで ssh ctr-test が通ることを確かめてから、Desktop に登録します。Windows 版の Desktop は内蔵の SSH クライアントを使い、ProxyCommand の実行に Git for Windows の sh が必要です。
  • 使い終わったコンテナは自動では消えません。docker rm -f、docker volume rm、git worktree remove で片付けます。
